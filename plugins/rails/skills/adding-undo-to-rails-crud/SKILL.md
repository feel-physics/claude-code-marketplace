# Rails アプリに「元に戻す」機能を付ける

Webアプリで「あ、間違えた！」と思ったとき、直前の操作を元に戻せると便利ですよね。
このスキルは、Railsで作ったアプリに**「元に戻す（undo）」ボタン**を安全に追加する方法を教えます。

## 基本の考え方：「スナップショットを撮ってから変更する」

変更する**前**の状態をスナップショット（その瞬間の記録）として保存しておいて、「元に戻す」が押されたら、そのスナップショットの状態に戻す。これだけです。

## いつ使うか

- 「元に戻す」「undo」「直前の操作を取り消す」をアプリに入れたいとき
- 1回の操作で複数のデータが変わるケース（例：順番の入れ替え）があるとき
- まずは直近1〜20回分を戻せれば十分なとき
- シンプルな実装を優先したいとき

こんな場面には向いていません：

- 「やり直し（redo）」も最初から必要なとき
- すべての変更履歴を監査記録として残す必要があるとき
- 外部サービス（メール送信など）まで巻き戻したいとき

## 仕組みのイメージ

### ふつうのアプリ（undoなし）

- データを直接書き換える
- 戻したいときは、戻す処理を自分で1つずつ書かないといけない

### このスキルを使ったアプリ（undoあり）

- **操作の記録**：「いつ、誰が、何をしたか」を1件記録する
- **変更前のスナップショット**：「その操作で変わるデータの、変更前の状態」を保存する
- **元に戻す**：最新の記録を1件取り出して、スナップショットの状態に戻す

### 3つのルール

1. **画面での1回の操作 = 1件の記録**
2. **変わったデータ1つにつき、スナップショット1枚**
3. **「元に戻す」はスナップショットの状態に戻すだけ**

## 早見表

| こんなとき | やること |
| --- | --- |
| データ1件を更新 | 記録1件 + スナップショット1枚 |
| 順番の入れ替え・上書き | 記録1件 + スナップショット2〜3枚 |
| 空のマスにデータを入れた | 「前は空だった」と記録しておく |
| 親データに紐づく子データも戻す | 子データの一覧をまるごとJSON形式で保存し、戻すときは全部入れ替え |
| 最小構成 | 「やり直し」なし、最新のものから順に戻す、最大20件まで |

## 実装の手順

### 1. どこでデータが変わるか調べる

コードを検索して、実際にデータを作成・更新・削除している場所をすべて見つける。
「1件だけ変わるケース」と「複数件まとめて変わるケース」に分ける。

### 2. どこまで戻せるようにするか決める

最初から全部を対象にしない。まずは範囲を絞る。
設計メモ（`design.md`）とタスクリスト（`tasklist.md`）に「ここまでやる」を書き出しておく。

### 3. データの保存先を設計する

2つのテーブルを作る：

- **操作の記録テーブル**（`*_actions`）：いつ何をしたか
- **スナップショットテーブル**（`*_snapshots`）：変更前のデータ

スナップショットテーブルには少なくとも以下を持たせる：
- どのレコードかを特定する情報（テーブル名やIDなど）
- そのデータが元々存在していたか
- 戻すべき値
- 必要なら、紐づく子データの一覧（JSON形式）

### 4. 「変更前」にスナップショットを撮る

ここが最重要ポイント。データを変更した**後**ではなく、**変更する直前**にスナップショットを撮る。
変更後に撮ろうとしても、もう元の状態は失われている。

### 5. 「元に戻す」処理はシンプルに

やることはこれだけ：

1. 最新の記録を1件取ってくる
2. その記録に紐づくスナップショットを見る
3. スナップショットの状態に戻す（1つのトランザクションで安全に）
   - 元々あったデータ → スナップショットの値に戻す
   - 操作で新しく作られたデータ → 削除する
   - 子データ → 差分を計算するより、まるごと入れ替えるほうが安全

### 6. 簡単なケースから作る

まずは「追加」「削除」「更新」の単純なケースを動くようにする。
そのあとで「順番の入れ替え」のような複雑なケースを追加する。

### 7. 最後は実際の画面で確認する

テストコードが通っても終わりにしない。
実際にブラウザでアプリを開いて、操作して、「元に戻す」ボタンを押して、ちゃんと戻ることを自分の目で確かめる。

## よくある失敗

- **最初から大掛かりな仕組みを作ろうとする**
  → まずはスナップショット方式で十分か試す。いきなり完璧を目指さない。

- **変更した後に記録を取ろうとする**
  → 変更後では「元の状態」がもう消えている。必ず**変更前**にスナップショットを撮る。

- **1件ずつしか考えない**
  → 「順番入れ替え」のように複数データが同時に変わる操作を、1つの記録にまとめないとundoが壊れる。

- **子データの戻し方を曖昧にする**
  → 差分を計算するより、変更前の一覧をまるごと保存して全部入れ替えるほうが確実。

- **テストが通ったら完了にしてしまう**
  → 最後は画面から実際に「戻せる」ことを目で確認する。

## うまくいった状態

良いundo機能は、こうなっている：

- 仕組みがシンプルで、人に説明しやすい
- 簡単なケースがまず動いている
- 複雑なケース（順番入れ替えなど）も同じ仕組みの上に載っている
- 画面から実際に「元に戻す」ができる
- 「どこまで戻せるようにするか」が設計メモに書いてある
